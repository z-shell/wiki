:::info Available since v1.3.0
Project configuration and automatic `zsh-lint.json` discovery are part of the
published v1.3.0 CLI. v1.2.0 accepts `--config` but has neither discovery nor
`--no-config`; v1.1.0 rejects `--config`.
:::

Project configuration gives rules explicit context that one syntax tree cannot
provide, such as whether a source is an executable, sourced plugin entrypoint,
autoloaded function, completion, or test fixture.

## How a configuration is found

When `--config` is omitted, the CLI starts in each input file's directory and
walks toward the filesystem root, using the nearest `zsh-lint.json`. Inputs
found under the same configuration are analyzed together as one project; inputs
under different configurations stay separate. A file with no configuration
above it, or one that matches no configured source root, uses the default rule
set.

| Option          | Effect                                                          |
| --------------- | --------------------------------------------------------------- |
| (none)          | Discover the nearest `zsh-lint.json` for every input.           |
| `--config PATH` | Use one explicit configuration for every input; skip discovery. |
| `--no-config`   | Disable discovery and keep the unconfigured default rule set.   |

`--config` and `--no-config` are mutually exclusive.

## Try the standalone example

The source checkout's `examples/standalone` and `examples/plugin` directories
contain the validated examples used on this page:

```sh
git clone https://github.com/z-shell/zsh-lint.git
cd zsh-lint
zsh-lint examples/standalone/script.zsh
```

Discovery picks up `examples/standalone/zsh-lint.json`. The explicit form gives
the same result:

```sh
zsh-lint --config examples/standalone/zsh-lint.json \
  examples/standalone/script.zsh
```

## Minimal configuration

```json
{
  "version": 2,
  "project": {
    "kind": "application",
    "minimum_zsh": "5.8",
    "identifier": "example-application"
  },
  "sources": [{"root": "script.zsh", "profile": "standalone-executable"}]
}
```

`project.identifier` is the one portable project identifier: lowercase ASCII
letters, digits, and hyphens, starting and ending with a letter. Namespace
rules derive shell-visible prefixes from it by replacing hyphens with
underscores; nothing is inferred from a repository or directory name.
`project.kind` is one of `plugin`, `theme`, `zi-annex`, `module`, `library`,
`tool`, or `application`.

Paths are relative to the directory containing the configuration. Every input
must stay under that directory and match one source root.

## Source profiles

| Profile                 | Use it for                                                            |
| ----------------------- | --------------------------------------------------------------------- |
| `standalone-executable` | A script launched as its own process.                                 |
| `startup-file`          | Files such as `.zshrc` or `.zprofile`.                                |
| `sourced-library`       | Plugin entrypoints and libraries loaded into an existing shell.       |
| `autoload-function`     | One function body loaded through Zsh `autoload`.                      |
| `test-fixture`          | Test inputs that should not inherit production lifecycle assumptions. |

The optional `completion` role is valid only with `autoload-function`.

## Plugin example

```sh
zsh-lint examples/plugin/example.plugin.zsh \
  examples/plugin/functions/example_run \
  examples/plugin/completions/_example \
  examples/plugin/tests/example-fixture.zsh
```

Configured analysis treats the complete explicit input list as one project.
Files you omit are outside cross-file validation.

For the strict schema and failure contract, see the
[source-adjacent project configuration contract](https://github.com/z-shell/zsh-lint/blob/main/docs/project/project-configuration.md).
